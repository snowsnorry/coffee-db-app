# Справочник разновидностей: интеграция с UI

## Назначение и текущая граница реализации

UI должен автоматически получать названия разновидностей из той же PostgreSQL-базы,
где хранятся товары. Ручная передача `dictionary.json` в UI больше не нужна после
реализации чтения справочника в backend UI-приложения.

В этом репозитории реализована команда `coffee-db load-variety-dictionary`:
она создаёт таблицы и индексы и публикует словарь. API и изменения UI ещё не
реализованы. Описанные ниже endpoint и формат ответа — предлагаемый контракт
для приложения, а не существующий API этого проекта.

## Таблицы

### `coffee_variety_dictionaries`

Одна строка на неизменяемую версию словаря.

| Поле | Тип | Значение |
| --- | --- | --- |
| `version` | TEXT, PK | Версия, например `coffee_variety_dictionary_v6` |
| `sha256` | TEXT | Контрольная сумма исходных байтов JSON-файла |
| `document` | JSONB | Полный словарь: metadata, canonical, mapping, contract, sources |
| `imported_at` | TIMESTAMPTZ | Время первого импорта версии |

Для обычного отображения UI нужны только `version` и при необходимости `sha256`.
Полный `document` содержит правила нормализации, исключения и обоснования решений;
передавать его на клиент при каждом запуске не требуется.

### `coffee_varieties`

Одна строка на каноническое название в конкретной версии.

| Поле | Тип | Значение |
| --- | --- | --- |
| `dictionary_version` | TEXT, FK | Ссылка на `coffee_variety_dictionaries.version` |
| `id` | TEXT | Канонический ID из словаря, без преобразований |
| `label` | TEXT | Название для отображения |
| `kind` | TEXT | Тип названия из словаря |
| `aliases` | JSONB, массив строк | Варианты написания для поиска по справочнику |

Первичный ключ — **`(dictionary_version, id)`**. Типы `kind`:
`variety_label`, `group_label`, `species_label`, `source_variety_label`.
Тип следует сохранять в API: не каждое название обозначает отдельный культивар.
Не нужно выводить вид растения или родственные связи из названия.

Помимо индексов первичных ключей, созданы индекс `(dictionary_version, label)`
и GIN-индекс по `aliases`. Они не означают, что реализован нечёткий поиск
или поиск по подстроке: такую логику backend определяет отдельно.

Таблица разновидностей — проекция `document.canonical`. Она загружается вместе
с полным документом одной транзакцией и отдельно не редактируется.

## Связь с товарами

В `coffee_products` уже сохраняются:

- `variety_dictionary_version`: версия, использованная при нормализации товара;
- `variety_ids`: JSONB-массив канонических ID или null;
- `variety_unresolved`: JSONB-массив неразрешённых исходных названий или null;
- `variety_raw`: исходные значения до нормализации.

Для каждого элемента `variety_ids` нужно найти строку, у которой одновременно
`dictionary_version = product.variety_dictionary_version` и `id = variety_id`.
Название берётся из `label`. В памяти клиента удобно держать вложенную карту
`dictionaryByVersion[version][id]`.

**Нельзя разрешать все товары через последний загруженный словарь.** Каталог
может содержать товары разных версий; новая публикация словаря не меняет
результат нормализации старых товаров. Отдельного указателя «активный словарь»
в текущей схеме нет. `imported_at` не определяет порядок версий.

Элементы `coffee_products.variety_ids` и поле версии товара сейчас не защищены
внешним ключом на справочник. Команда `load-coffee` пока не проверяет наличие
этих записей. Поэтому порядок публикации и обработка отсутствующих соответствий
в backend остаются обязательными.

## Загрузка при запуске UI

Рекомендуемый поток:

1. Backend определяет непустые версии словаря, используемые товарами каталога.
2. Читает метаданные этих версий и их строки из `coffee_varieties`.
3. Возвращает компактные справочники, сгруппированные по версии.
4. UI строит карту соответствий и использует её для карточек и фильтров.
5. Если позднее приходит товар с ещё не загруженной версией, UI догружает именно её.

Например, можно реализовать `GET /api/coffee/variety-dictionaries` со структурой:

```text
{
  dictionaries: [
    {
      version: string,
      sha256: string,
      varieties: [{ id: string, label: string, kind: string, aliases: string[] }]
    }
  ],
  missingVersions: string[]
}
```

`missingVersions` перечисляет версии из товаров, отсутствующие в таблице словарей.
Для текущего v6 справочник содержит 902 строки, поэтому его можно загрузить целиком.
Если API уже возвращает названия вместе с товарами, разрешение ID можно целиком
выполнять на backend; правила сопоставления остаются теми же.

Кэшировать данные следует по версии; `sha256` можно использовать как дополнительный
идентификатор содержимого. Уже опубликованная версия неизменяема, но перечень
используемых каталогом версий нужно обновлять. Контрольная сумма вычислена по
байтам исходного файла: не сравнивайте её с хешем сериализованного ответа API
или JSONB-документа, поскольку форматирование может отличаться.

## Отображение и неполные данные

- Подтверждённые сопоставления отображаются через `label` в порядке `variety_ids`.
- `variety_unresolved` отображается отдельно исходным текстом, при необходимости
  с пометкой «не уточнено». Эти значения не становятся каноническими ID.
- Если оба массива пусты или null, UI показывает отсутствие данных.
- Если версия или ID не найдены, backend фиксирует нарушение целостности,
  а UI показывает нейтральную заглушку для отсутствующего названия. Товар
  продолжает отображаться; подставлять похожий сорт или другую версию нельзя.
- Не добавляйте весь `variety_raw` к нормализованным названиям: там могут быть
  значения, которые словарь явно исключил как не относящиеся к разновидностям.

`aliases` полезен для поиска названия пользователем, но не заменяет `mapping`.
Правила нормализации могут сопоставлять одну строку нескольким ID, исключать её
или содержать решение для отдельного товара. UI не должен повторно нормализовать
исходные значения по массиву aliases.

## Фильтры и счётчики

Опции фильтра лучше строить по каноническим ID, реально встречающимся в текущем
каталоге, и дополнять названиями из соответствующей версии справочника.
Счётчики рассчитываются по текущим товарам с учётом выбранных фильтров.
`product_count` внутри полного документа — историческая статистика построения
словаря; использовать её как актуальное количество товаров нельзя.

Базовый идентификатор опции фильтра — пара `(dictionary_version, id)`.
Фильтрация проверяет и версию товара, и наличие ID в его `variety_ids`.
Если UI объединяет опции разных версий в одно название, backend должен явно
передавать список соответствующих пар; совпадения текста `label` недостаточно
для решения об эквивалентности. Один товар учитывается в счётчике объединённой
опции только один раз.

## Публикация и обновление

При настроенном `DATABASE_URL`:

```bash
# Наибольший номер каталога vN в data/coffee-varieties, сейчас v6.
coffee-db load-variety-dictionary

# Явно выбранный словарь.
coffee-db load-variety-dictionary --input data/coffee-varieties/v6/dictionary.json
```

Автовыбор относится только к CLI и ищет файлы относительно исходников проекта.
Он не выбирает версию для отображения товаров. При установке без файлов словарей
нужно передать путь через `--input`.

Публикуйте словарь перед импортом товаров, которые на него ссылаются.
Для существующего каталога загрузите все используемые версии.
Повторный импорт идентичного файла пропускается; другая контрольная сумма
при прежнем `metadata.version` вызывает ошибку. Даже изменение форматирования
исходного файла меняет сумму. Для изменённого словаря нужна новая версия.

Таблицы, индексы, полный документ и канонические строки публикуются одной
транзакцией. Одновременные запуски импортёра сериализуются. При ошибке частично
загруженный справочник не становится доступным. Старые версии сохраняются;
не удаляйте версии, на которые ещё ссылаются товары.

## Проверка интеграции UI

- После запуска названия появляются без загрузки файла пользователем.
- Два товара с разными версиями получают названия из своих справочников.
- Неизвестное исходное значение отображается как неуточнённое.
- Отсутствующий словарь или ID не ломает карточку и не вызывает подмену названия.
- Новая версия догружается без очистки справочников старых товаров.
- Фильтры и счётчики соответствуют текущему каталогу, а не статистике файла.
